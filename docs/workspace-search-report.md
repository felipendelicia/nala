# Workspace, templates and search — Task 3

## Implemented interfaces

- `lib/workspace/document_workspace.dart`: `DocumentWorkspace` owns one `EditorController` per open notebook, independent of the visible panes. `open`, `select`, `splitWith`, `focus`, `close` and `flush` coordinate tabs. `WorkspaceScreen(services:, initialEntry:, cloud:, initialPageIndex:)` is the Library route. Editors remain mounted in a keyed Stack while hidden, retain their viewport/state, and receive a pane-sized MediaQuery. Exactly one editor is `active`. `registerClose` is awaited before flushing or disposing; save failure retains the tab.
- `lib/templates/template_store.dart`: `PageTemplate` exposes `id`, `name`, `width`, `height`, `background`, `coverAssetId`. `TemplateStore(root:, assets:, pdf:)` exposes `load`, `importPdf`, `importImage`, `remove`. Built-ins: blank, ruled, grid, dots, Cornell and weekly. Own templates are saved atomically in `<account root>/templates/registry.json`, with a shared per-path queue for simultaneous split-pane imports. AssetStore retains original media by hash. Each imported PDF page becomes a template with its original dimensions/page reference and a raster image for its cover. Image imports accept valid PNG/JPEG up to 50 MB and 40 megapixels. PDF template imports currently require an unprotected PDF.
- `lib/templates/template_picker.dart`: `showTemplatePicker(context, store:)` returns the selected template, shows previews, imports PDF/image files, and removes own templates. Applying a template as paper, adding a page or using a cover is performed through the editor controller by the parent integration.
- `lib/search/search_service.dart`: `SearchService(pdf:, assets:)` exposes `search(notebooks, query, cancellation:, onProgress:)`. `SearchHit` has `notebookId`, zero-based `pageIndex`, `snippet`, `kind`. Search handles titles, subjects, comments, text objects, original PDF text and recognized text. Accent/case/whitespace normalization covers Spanish. Native extraction cache is bounded to 128 pages/1,000,000 characters, keyed by immutable asset hash and PDF page. Results include page-level failures and cancellation. Scanned PDF pages with no text layer produce no invented text.
- `PdfService.extractText(String assetId, int pageNumber, {PdfRenderCancellation? cancellation}) -> Future<String>` uses the existing rendering queue, session password store and PDFium lifecycle. All documents are disposed; cancellation discards stale results.
- `lib/search/notebook_search_dialog.dart`: `NotebookSearchDialog(notebooks:, pdf:, assets:, onOpen:, onRecognized:)`. The dialog handles progress, cancellation, partial-result notices, local recognition availability, explicit model download/delete and manually corrected text. **The dialog pops itself before calling `onOpen`; that callback must not pop a second route.**
- `Future<String> pageRecognitionFingerprint(NotebookPage page)` is exported from `search_service.dart`; it hashes page dimensions, original background, strokes and objects, excluding recognized text. The callback typedef is `Future<bool> Function(String notebookId, String pageId, String fingerprint, String text)`. Return false when a late recognition result cannot safely be saved. Search ignores stale recognized text. Library reloads the repository head after asynchronous hashing and checks its unchanged revision ID before committing cache text.

## Recognition

Android registers `nala/ink-recognition` through `InkRecognitionBridge`. Methods: `status`, `download`, `delete`, `recognize`, `cancel`. The bridge sends original stroke coordinate sequences to the local Spanish ML Kit digital ink recognizer, refuses recognition without a downloaded model, bounds input size, returns the top candidate without manufacturing text, and closes its recognizer with the activity. A cancelled operation settles its Flutter result and discards any later native result.

The dependency is `com.google.mlkit:digital-ink-recognition:19.0.0`. The current 19.0 API namespace is `com.google.mlkit.vision.digitalink.recognition.*`. Verified against [official Android guide](https://developers.google.com/ml-kit/vision/digital-ink-recognition/android) and the [official ModelManager sample](https://github.com/googlesamples/mlkit/blob/master/android/digitalink/app/src/main/java/com/google/mlkit/samples/vision/digitalink/recognition/ModelManager.java).

Linux probes for `tesseract` and the installed `spa` model; it never installs either automatically. When available it rasterizes the page locally, runs OCR with a bounded timeout and supports cancellation. The interface explicitly describes it as OCR for printed text/scans and states that handwriting may fail. This development environment has no Tesseract installed. Corrected Android text is persisted in notebook page fields and therefore travels through the existing notebook sync to Linux.
